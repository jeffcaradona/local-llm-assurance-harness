## High severity (each verified by execution)

### 1. `npm start -- --help` fails on a fresh clone

`package.json` runs `node --env-file=.env`, and Node hard-errors when the file is missing:

```text
node: .env: not found
```

The prompt's acceptance criteria begin with "Help and example commands work." Every documented `npm start` command fails until `.env.example` is manually copied.

**Fix:** use `--env-file-if-exists=.env` (supported on Node ≥ 22.9, within the documented baseline).

### 2. Unhandled rejection crashes the process with a raw stack trace

`src/filesystem/collector.js:18` eagerly starts `realpath(resolve(rootPath))` at construction time. If the review fails before anything awaits that promise — e.g. `review --root /nonexistent` with no `--request` — the structured error prints, and _then_ Node crashes on the orphaned rejection. Reproduced directly.

This is exactly the "detached promise" the prompt forbade, created in the composition path.

**Fix:** resolve the root lazily inside the first call that needs it, or validate the root up front in the CLI/orchestrator before constructing the collector.

### 3. Findings can cite evidence the model never saw

`src/orchestrator/reviewOrchestrator.js:106` verifies model references against `[...includedEvidenceIds, ...omittedEvidenceIds]`. Omitted evidence was, by definition, _not_ in the prompt — yet a finding citing an omitted ID passes verification (confirmed with a direct call to `verifyEvidenceReferences`).

The prompt is explicit: "Validate every reference against evidence supplied to the model — not merely evidence collected earlier." This undermines the project's central provenance claim.

**Fix:** require `findings[].evidenceIds ⊆ includedEvidenceIds`; only `limitations.omittedEvidenceIds` may reference omitted IDs.

### 4. Environment restriction for subprocesses is a no-op

`src/subprocess/runner.js:35` builds the child environment as `{ ...process.env, ...env }`, so the collector's deliberate `env: {}` (`src/filesystem/collector.js:78, 100`) restricts nothing — `fd` and `rg` inherit the full parent environment, API keys included. Verified: a child spawned with `env: {}` still sees parent secrets.

The prompt required restricting inherited environment variables, and `docs/threat-model.md` claims it.

**Fix:** build from a minimal base (`PATH`, plus `SystemRoot`/`ComSpec` on Windows) instead of spreading `process.env`.

### 5. Windows drive-letter paths defeat both containment checks — in opposite directions

All three containment helpers (`src/filesystem/collector.js:13`, `src/capabilities/registry.js:30`, `src/audit/manifest.js:27`) only test for `..` prefixes. On Windows, `path.relative('C:\\repo', 'D:\\evil')` returns an _absolute_ path that doesn't start with `..`, so:

- `registry.js` / `collector.js`: a path on another drive **passes** containment (escape not caught).
- `manifest.js`: an output directory on another drive is **wrongly rejected** as "inside the repo".

The project targets Windows development and CI runs `windows-latest`, but no test covers cross-drive paths.

**Fix:** treat `isAbsolute(rel)` as escaping (and as "outside", in the manifest check); add Windows-conditional tests.

## Medium severity

### 6. `filesystem.searchText` bypasses the sensitive-path policy entirely

The `E_SENSITIVE_PATH_BLOCKED` check exists only in `readTextFile` (`src/capabilities/registry.js:62`). Search matches from `credentials.json`, a committed `.env`, or a key file flow straight into evidence. `rg`'s default gitignore behavior mitigates this by accident, not by policy — and the prompt demands "policy enforcement must exist in code, not merely in prompts."

**Fix:** filter match paths through `isLikelySensitivePath` in the `searchText` capability.

### 7. A mistyped `--file` produces `E_INTERNAL "Unexpected harness failure"`

The `realpath` ENOENT in `assertPathContained` is unmapped; the orchestrator's `asHarnessError` swallows it into the generic bucket. The most common operator error deserves a stable `E_FILE_NOT_FOUND`. The same applies to a missing `--instructions` file in `src/context/compiler.js`.

### 8. `collector.collect()` / `toEvidenceItems()` are dead code that diverges from the live path

The orchestrator reimplements collection (`src/orchestrator/reviewOrchestrator.js:59-89`) with its own copies of `makeEvidenceId` and evidence-meta assembly; nothing calls `collect()`. The dead copy already disagrees with the live one (no sensitive-file skip, byte-budget check applied differently, and a nested `break` that only exits the inner loop). Classic agent-generation drift: two parallel implementations, one abandoned mid-refactor.

**Fix:** delete `collect`/`toEvidenceItems` from the collector, or move collection into the collector and have the orchestrator call it — not both.

### 9. Replay doesn't actually replay prompt compilation

The prompt requires "deterministic prompt compilation" during replay. The bundle stores pre-compiled prompt strings, and `src/orchestrator/replay.js` only re-validates the review and re-renders the report — it never recompiles anything, and the stored prompts aren't checked against anything. The README's "sanitized inputs needed for deterministic offline replay" overstates what replay does.

**Fix:** store the evidence items in the bundle and rerun `compilePromptContext` during replay, or correct the documentation.

### 10. Subprocess termination is fire-and-forget

On timeout/abort, `src/subprocess/runner.js` sends one SIGTERM, rejects immediately, and `removeAllListeners()` discards the `close` handler — so a child that ignores SIGTERM leaks silently and its exit is never observed. There is no SIGKILL escalation and no wait-for-exit after kill. The README documents the _descendants_ limitation honestly, but not this one.

**Fix:** keep a `close` listener alive after kill, escalate to SIGKILL after a short grace period, and document the actual guarantee.

### 11. Node version claims contradict each other

- README: "22.x and 24.x LTS (`>=22.0.0 <25`)"
- `package.json` engines: `">=22.0.0 <=26"` (semver-expands to allow 26.x, which doesn't exist)
- CI matrix: 22 and 24

The prompt specifically asked for a verified, documented baseline.

**Fix:** use `>=22.0.0 <25` everywhere.

### 12. Truncated `rg` output turns a large result set into a hard error

Search relies on the 2 MB stdout cap; a cap hit mid-line makes `JSON.parse` fail → `E_SEARCH_OUTPUT_INVALID` for a perfectly valid search. Also, `fd` runs with `--hidden` while `rg` keeps its default hidden/gitignore filtering — discovery and search silently cover different file sets, which brushes against the prompt's "do not silently substitute different search behavior."

**Fix:** pass `--max-count` (and consider `--max-filesize`) to `rg`; tolerate a truncated final line when `stdoutTruncated` is set; document the fd/rg coverage difference.

- Honest limitation language in the README and threat model.
- The "no hosted fallback, reject repaired JSON" requirements are correctly implemented.
